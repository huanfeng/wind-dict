# 用户词典走 MDX，且运行时直读而非导入

用户可以把自己下载的 **MDX 词典**放进来直接查：不导入、不转换、不预处理。实现在
`src/store/mdx`，只新增 `flate2` 一个依赖。

这份 ADR 推翻 ADR-0001 的一半，并纠正本项目自己在几小时前做出的一个错误判断。

## 为什么现在可以做 MDX 了

ADR-0001 写下的否决条件是：「**除非 windui 获得富文本渲染能力**，否则重新考虑 MDX
都是错的。」该条件已经满足——windui 有了 `RichDoc` 与斜体，本 crate 有了
`crate::html`。

但要诚实地说清楚满足了多少：**富文本 ≠ HTML+CSS 渲染器**。ADR-0001 真正拒绝的是
后者，而现在建成的是一个有界的标签映射器。层级信息仍然会丢（`crate::html` 的模块
文档里量化了确切代价）。所以用户词典是**补充**，不取代随程序分发的结构化词库——
ADR-0001 关于「离线释义简略但可靠」的取舍原样成立。

## 为什么不是「导入成 SQLite」

本项目先前的结论是「运行时读 MDX 必须落成一次性导入」，理由是整本词典会进内存。
**那个理由是错的**，而且错得有代表性：它来自 `readmdict` 这个 crate 的接口（只有
`items()`，一次读全部），却被当成了**格式**的性质。

实测直接推翻它。用 ECDICT 1.0.28 的 `ecdict-mdx-headless-28.mdx`（69.7 MB，
3,402,564 词条）：

| | 代价 |
|---|---|
| 开库读入（= 常驻索引） | **0.09 MB**，全文件的 0.14% |
| 开库耗时 | 2.1 ms |
| 查一个词 | 读盘约 30 KB，耗时 1.3 ms |
| 瞬时解压峰值 | 64 KB |

原因是 MDX 的索引本就是**两级**的：文件头附近只记每个 key block 的首末词，逐词表压
在块里。查词 = 二分定位块 → 解压那一个 → 定位正文块 → 解压那一个。常驻内存是
O(块数) 而非 O(词条数)，与 ADR-0006 要的形状一致。

判据记在这里：**一个库的 API 局限不是数据格式的性质**。分不清这两者，就会把「我手上
的工具做不到」写成「这件事做不到」，然后据此改架构。

## 为什么是 MDX，不是 StarDict 或 eudic

三个候选的分野不在质量，在**有没有可依据的规范**：

- **StarDict** 有官方规范（`StarDictFileFormat`，随 GPL 源码分发，字节级定义完整），
  且天生适合随机访问——`.idx` 排好序可 mmap 二分，`.dict.dz` 用 dictzip（gzip 加一张
  块偏移表）。实测 ECDICT 的 StarDict 版甚至是未压缩的 `.dict`，可直接 seek，且
  `sametypesequence=m` 意味着正文是纯文本、零 HTML。**技术上它比 MDX 更省事。**
- **MDX** 无官方规范，但有稳定的事实标准（逆向文档，GoldenDict 与各语言实现都照它）。
- **eudic** 是私有格式，**AES192 加密且主密钥在欧路程序里**。有人逆出来过，但明确
  不公开工具。绕开厂商加密密钥读它自家格式，与读一个公开文档化的格式是两回事。

选 MDX 而非更省事的 StarDict，理由只有一条：**生态**。中文词典社区（PDAWIKI 等）的
精品词库绝大多数是 MDX，只做 StarDict 等于把这个功能做给一个不存在的词库池。
StarDict 日后可加，成本比 MDX 低。

## 键序必须精确复刻，否则静默漏词

MDX 的键按「小写 + 去掉 ASCII 标点空白」排序，规则由文件头的 `KeyCaseSensitive` 与
`StripKey` 声明。这不是可以近似的细节。在上述真实词典的全部 340 万键上实测：

| 比较函数 | 逆序对 | 随机 3000 键命中 |
|---|---|---|
| 仅 `lower()` | 510,108 | 2468 / 3000 |
| mdict-js 文档里的字符集 | 1,861（漏了 `&`） | —— |
| 「非字母数字全去」 | 6,795（连重音字母一起吃） | —— |
| **ASCII 标点空白全去** | **0** | **3000 / 3000** |

漏掉的 17.7% **不报错**，只显示「未收录」——用户会以为词典里没有这个词。这类缺陷
没有任何症状可循，只能靠这样的批量反验发现。

归一化必然产生重名（实测 199,037 组，最大一组 15 个）。故查词返回**一组**结果而非
一条：真实查询 `full-house` 得到 `full-house` / `full house` / `fullhouse` 三条不同
词条，MDict 自己也是一并列出。少返回不是「精确」，是丢词条。

## 装一本词典 = 把文件放进一个目录

用户词典**扫目录**，不逐个登记：`Settings` 存的是一个目录和一份「关掉了哪几本」的
名单，不是一串文件路径。

起初做的是「设置页选文件 → 加进列表」。那个交互多了一遍无用功：用户已经在文件管理器
里把词典下载、解压、放好了，选文件不过是**再向程序汇报一遍他刚做过的事**。扫目录之后
设置页只剩两件事——换目录、关掉某一本，两件都是文件系统表达不了的。

三处随之确定：

- **默认全部启用**，设置里存的是**禁用**名单。反过来存「启用」的话，新丢进去的词典
  会默认关闭，「放进去就能用」就退化成「放进去再来开一下」，与逐个添加没有区别。
- 开关按**文件名**记，不按完整路径。用户把词库从 C 盘挪到 D 盘之后，这些开关还认得
  出是同一本词典。
- **递归三层**。MDX 常以「一本词典一个文件夹」分发（`.mdx` 加同名 `.mdd` 资源包和一个
  `.css`），只扫平铺会把整包漏掉；而无限深会在用户把目录指到下载文件夹时变成全盘遍历。

默认目录是**用户数据目录下的 `dicts`**，不是部署目录下的。这不是偏好：`dev.ps1` 卸载
会 `Remove-Item -Recurse -Force` 整个部署目录，而这里放的是用户自己下载的、动辄几百 MB
的文件。把默认目录放进去，等于让「卸载程序」顺手删掉用户的词库——与 ADR-0011 把收藏
和历史挪出部署目录是同一条理由。目录本身可改，因为词库大到用户多半有自己的存放地方。

## 明确不支持的两件事

- **LZO 压缩块**（多见于 1.2 版老词典）。不做的理由不是难度，是**没有测试向量**：
  LZO1X 解压是个指针状态机，写错了不崩溃，只产出错乱的字节；本机装不上
  `python-lzo`（无预编译轮子），拿不到可信对照。一个没测过的解压器比明确报错更糟。
  日后若有真实样本，补上是小事。
- **正文加密**（`Encrypted` 含 1 位，需 MDict 注册码）。不打算支持。

两者都在**打开阶段**就报错并点名原因，不留到查词时给出无从归因的空结果。

## 后果

- 新增依赖 `flate2` 一个（zlib 解压）。ripemd128、键序归一化、样式表展开都在本仓库
  自己写了——只有解压是绕不过去的那一环。
- `windows` crate 增加 `Win32_Globalization` feature：老词典的 GBK / Big5 正文靠
  `MultiByteToWideChar` 解码。系统自带这些代码页的映射表，引一份静态编码表进二进制
  去做同一件事不划算。
- 测试样本入库（`tests/fixtures/mdx/`，5 份共约 5 KB），覆盖引擎版本、键索引加扰、
  压缩类型、正文编码四条分叉。**造出来的样本只有一个块**，块之间的二分与跨块等值组
  只有真词典能验，故另有一个「放一份到 `.cache/dict/test.mdx` 即启用」的用例，
  与字形库同一套办法。
- 随程序分发的数据文件**没有变化**。用户词典是用户的文件，不进 `THIRD-PARTY.md`——
  那份文档记的是我们分发什么，不是用户能读什么。
- `dev.ps1` 多一个 `gm` 命令：下载一本示例 MDX 供手动测试，部署时装进词典目录（那里
  已有词典就不动）。取 ECDICT 自己发布的 **headless**（无音标）版是刻意的——它与随
  程序分发的 `ecdict.db` 同源，若取带音标的版本，两段显示出来几乎一样，反而看不出
  用户词典那一段是不是真的走通了。它**不随产品分发**，只在开发机的 `.cache/` 里。
