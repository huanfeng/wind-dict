# 进程常驻托盘，靠 SQLite 按需读页而非不常驻来控制内存

需求同时要求「后台内存占用低」与「快捷键快速唤起」。这两者看似冲突，我们选择**常驻**——进程始终运行、隐藏于托盘，热键只改变窗口可见性（见 CONTEXT.md「唤起」）。这个选择需要记录，因为「要内存低所以别常驻」是一个显而易见、且错误的推论。

## 为什么常驻不等于费内存

内存大头从来不是进程本身，而是词库。windui 的空窗口私有内存实测仅 **3.65MB**（README 实测数据，520×560 窗口）。而词库有 76 万词条，若启动时反序列化进内存则必然爆炸——但 SQLite **按需读页**，配合显式钳死的 `cache_size`，常驻进程的驻留内存与词库总量基本脱钩。

也就是说，真正决定内存的是**词库的载入方式**，不是进程的存活与否。把进程杀掉来省那 3.65MB，代价是每次唤起都要付出进程创建 + 数据库打开的延迟——用词典最核心的体验，换一个几乎可忽略的内存数字。

## 被拒绝的方案

**不常驻，每次冷启动**：热键由 Windows 快捷方式的「快捷键」字段触发，`App::single_instance` 转发 argv。后台内存真正为零，且零新增平台代码。拒绝原因有二：唤起延迟直接损害核心体验；且快捷方式热键只支持 `Ctrl+Alt+字母`，无法实现词典常见的双击键（如 `Ctrl+Ctrl`）。

**常驻热键守护 + UI 进程按需拉起**：后台内存最低。拒绝原因是双进程生命周期、IPC、崩溃恢复的复杂度，换来的收益相比常驻方案只有几 MB。

## 实测验证（2026-07 上旬）

> **本节数据已作废**，需求与配置均已改变——见文末「2026-07 修订」。保留原文是为了留下论证的来路，不是因为它仍然成立。

本决定的核心论证——「驻留内存与词库总量脱钩」——已用真实词库验证：

| 指标 | 实测值 |
|------|--------|
| 词库文件 | **172.9 MB**（英汉 157.6 + 汉英 15.3，共 895,343 词条） |
| 进程**私有内存** | **1.4 – 3.2 MB**（随负载浮动） |
| 工作集 | 5.3 – 6.9 MB |
| 打开词库耗时 | 1.3 ms |
| 内存 / 词库比 | **约 0.8 – 1.8%** |

私有内存的浮动源于负载而非词库数量：轻负载（少量查询）约 1.4 MB；重负载（单字母前缀补全需排序约 5 万行）约 3.2 MB。**后者才是设计依据**——它是补全的真实最坏情况。

172.9 MB 词库对应个位数 MB 私有内存，论证成立。加上 windui 窗口（README 实测 3.65 MB），常驻总量预计在 7–10 MB 量级。

当时的配置是 `cache_size = -2000`（2 MB 上限）、`journal_mode = OFF`（只读库无需回滚日志）。现值见 `store/ecdict.rs` 的 `tune()` 与 `store/cedict.rs::open`。

## 后果

- ~~「内存占用低」这一需求的达成，**责任落在 SQLite 的 `cache_size` 配置与查询模式上**，而非进程架构。~~ **此条已失效**：需求本身已取消，`cache_size` 也确实被调大了——见文末修订。仍然成立的是「驻留内存与词库总量脱钩」。
- 必须提供退出途径（托盘右键菜单），因为关闭窗口不再等于退出进程。
- 需要处理开机自启（否则常驻的价值在重启后消失）。此项尚未决定。

## 2026-07 修订：不再以「后台内存尽可能小」为目标

**需求变了**：项目改为优先响应速度与渲染质量，不再追求极小的内存占用。据此有两处改动——渲染默认走 GPU（`App::renderer(Renderer::Auto)`；windui 0.13 之前这个开关叫 `accelerated(true)`，布尔型答不了「拿不到 GPU 怎么办」，现已拆成 Auto/Software/Gpu 三档，我们取自动回退的 Auto），词库页缓存从 2MB 放宽到 32MB（英汉）/ 8MB（汉英）。

**本 ADR 的决定不受影响**，但其论证的**重心变了**，必须说清楚：

原文说「内存占用低这一需求的达成，责任落在 SQLite 的 `cache_size` 配置上」。这句话在需求改变后已不适用——现在没有那个需求了。仍然成立的是更根本的那一条：**驻留内存与词库总量脱钩**。173MB 词库对应几十 MB 进程内存，且**不随词条数增长**（新增开销全是定值，见下方归因）。

「常驻」这个决定本身与内存无关：它买的是唤起延迟，而那是核心体验。当初之所以要论证内存，是因为有人会从「要省内存」推出「别常驻」——那个推论今天依然是错的，只是前提没了。

### 实测（release 构建，空闲态，同一台机器）

| 配置 | 私有内存 | 工作集 |
|------|---------|--------|
| 原始：软渲染 + 2MB 缓存 | 1.4 – 3.2 MB | 5.3 – 6.9 MB |
| 软渲染 + 32/8MB 缓存 | **13.5 MB** | 29.8 MB |
| **GPU 加速 + 32/8MB 缓存（当前）** | **38.6 MB** | 59.5 MB |

归因：**GPU 后端约 +25MB**（D3D 设备与交换链），**缓存放宽约 +10MB**。两者相加即从 3MB 到 38MB 的全部差额。GPU 是大头，缓存是小头——若日后要压回去，先关加速比先调缓存有效得多。

> 注意**别再用「内存 / 词库比」来论证脱钩**了。原文引用 0.8–1.8% 是有效证据，而现在这个比值（38.6/172.9 ≈ 22%）被约 25MB 的 GPU 常量主导，而 GPU 开销与词库大小毫无关系——词库若翻十倍，比值会掉到 2%，说明它度量的根本不是脱钩。真正支撑结论的是：**缓存上限 40MB 与 GPU 的约 25MB 都是定值，不随词条数增长**。

> 缓存在**空闲态**就吃掉约 10MB，值得留意：`cache_size` 是上限而非预分配，空闲却已占用，说明启动路径上已经有查询在读页（侧栏历史读取、补全器首次 `on_update`）。这不是问题，但它意味着「空闲」并不等于「没查过」。

### 后果

- **不再需要为内存数字辩护**，但「与词库总量脱钩」这条仍需守住：若将来引入全表扫描式查询或把词库整体载入内存，本 ADR 的论证即失效。
- GPU 加速在无可用 GPU、RDP 远程会话、离屏截图等情形下由 windui 自动回退软渲染，不会失败。故**截图验证走的是软渲染路径**——GPU 路径的渲染差异截图看不出来，只能真机看。
- 原文「配置见 `store/ecdict.rs` 的 `tune()`：`cache_size = -2000`」已过时，现值见该函数。

## 2026-09 修订：改为零窗口常驻，窗口关掉即销毁

**需求又变了，且是把上一节那条反转回来**：后台占用重新成为目标。落地不是去调缓存或关
GPU，而是换掉「常驻」的形态——从 `App::new(..) + hide_on_close + start_hidden`（留着一个
隐藏的主窗）换成 windui 的**零窗口常驻** `App::resident(..) + run_resident()`：进程平时
一个窗口都没有，托盘点击、全局热键、二次实例三条路按需 `open_window`，窗口关掉即销毁，
渲染资源随 `WindowState` 的 drop 归还。

**为什么不是「隐藏时卸载资源」**。那是这次需求最直觉的读法，而上游判定它走不通：症结不在
缺少释放机制，而在最后一个窗口 `WM_DESTROY` 时无条件 `PostQuitMessage`——窗口根本关不掉，
`hide_on_close` 才不得不把它吊着。修法是让窗口真能关，而不是给隐藏加一个卸载钩子；后者
等于维护「窗口活着但资源没了」这个中间态，它的每一处读取都要判一次。

**本 ADR 的决定仍然不变**：进程照常常驻，热键唤起照常没有进程创建与开库延迟——窗口的
建与毁是毫秒量级，词库句柄、用户数据、查询状态全都活在窗口之外的 `State` 里，关窗一个
都不丢（这也正是换肤能整树重建的同一条性质）。变的只是「常驻」期间**桌面上有没有一个
藏着的窗口**。

### 实测（2026-09-15，dev 构建 + `--renderer software`，同一台机器）

| 状态 | 私有内存 | 工作集 |
|------|---------|--------|
| 零窗口（`--tray` 启动，即开机自启的形态） | **6.22 MB** | — |
| 窗口开着 | 17.6 MB | 39.8 MB |
| 关窗后 | **6.99 MB** | 29.3 MB |

开关一次来回归还约 **10.6 MB**，且热键连按三次（开 → 收 → 开）内存同步在两档之间来回，
不累积。旧形态（`hide_on_close`）在同一处是**一分不还**——那份按物理像素分配的后备缓冲
随隐藏的窗口一直挂着。

两条**必须写明的口径限制**，别拿这组数去对比上一节那张表：

- 这是 **dev 构建**（未优化）且**软渲染**。软渲染是为了与上游那组数同口径；代价是它测不到
  本次改动在 GPU 路径上的收益，而按上一节的归因，D2D 设备与交换链约 **+25MB**，它同样随
  窗口销毁归还——**GPU 路径的实际收益应当更大，但尚未实测**（测它要占用全局热键与单实例
  锁，而验证时机器上正跑着一个 release 实例，不动它）。
- 空闲 CPU：关窗后 6 秒累计 CPU 无增长，零窗口不轮询。

### 后果

- **「后台内存尽可能小」重新成为目标**，但责任落点与最初那版仍然不同：它现在落在**窗口的
  生命周期**上，而不是 `cache_size`。缓存与 GPU 那两笔（约 10MB + 约 25MB）里，GPU 那笔
  **按归因预期应随窗口销毁一并归还，但尚未实测**（上面那组数走的是软渲染）；缓存那笔仍
  常驻——若日后还要再压，先动的是它。
- **窗口的一切配置从此写在 `ui::build` 的工厂里**（尺寸、下限、无边框、单例键、快捷键），
  不再在 `main` 的 `App` 构建链上。托盘、热键、启动即开窗、离屏截图**四处共用同一个工厂**：
  各写一份的话，截图验的就不再是用户看到的那个界面。
- **快捷键改挂窗口**（`Window::on_shortcut`）。`App::on_shortcut` 在这个模式下无处可挂，
  挂错地方的表现是「界面正常，所有 Ctrl+X 静默失灵」——为此在上游补了这个接口（ADR-0004）。
- **热键的显隐判据换成 `window_open(key)`**：常驻下窗口是「开着或不存在」两态，
  `window_state().visible` 恒为 `UNKNOWN` 的 `true`，照搬旧写法会恒走收起那一侧、按下去
  毫无反应。
- **二次实例要自己把窗口开出来**：平台层「返回后显示并前置主窗口」那条路没有主窗可前置，
  已改为绕一趟 `App::channel` 回到 UI 线程再 `open_window`。
- 截图验证仍然成立，但要给 windui 指明对象（`App::screenshot_window`）——常驻应用没有主窗，
  不指明只会截出一张空图。
- **窗口自身的状态每次唤起都是新的**，这是本次改动真实的代价，别只清点 `State`：用户拖过
  的**尺寸与位置**不再保留（故 `Window` 上补了 `.centered(true)`，否则 Windows 的级联偏移
  会让窗口一次比一次往右下走），**滚动位置**（`scroll_y` 是节点字段）与焦点、hover 同样
  归零。查询词、历史、展开态活在 `State` 里，不受影响。要保住前面那几样，得把它们分别提到
  `Settings`（几何）或 `State`（滚动）里去——尚未做。
