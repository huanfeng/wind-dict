# 字形属于字，不属于词条

汉字的部首、笔画与繁简对应（**字形**）独立成一层，按**字**查询，不做成 `Entry` 的第三个分支，也不作为字段挂在 `ChineseEntry` 上。数据存在单独的 `unihan.db`，源自 Unicode 官方的 Unihan 数据库。

## 为什么不挂在词条上

`行` 有三个读音，因而有**三条**汉英词条（`hang2` / `heng2` / `xing2`），却只有**一副**字形：部首 行、总 6 画。把字形挂到 `ChineseEntry` 上，这副字形要存三份，并且在类型上宣称「字形随读音而变」——它不变。

反方向同样不成立：`苹果` 是一条合法的汉英词条，而「苹果的部首」不是一个有意义的问题。挂上去就必须是 `Option`，于是每一处使用都要处理一个**在词条层面永远无法判定**的空值。

这与 ADR-0009 拒绝合并两类词条是同一个论证的另一面。那次拒绝的是「把两种形状塞进一个类型」，这次拒绝的是「把字的属性塞进词的记录」。若那次不合并是对的，这次不挂载就是对的。

后果是渲染层必须同样守住：字形画在**词头卡片**上，不画在词条里。画进 `chinese_doc` 会让 `行` 的字形重复三遍——数据模型里避开的重复，在像素上重新引入等于白避。

## 为什么不做成第三类词条

字形没有释义。一个只有部首笔画、没有任何解释的「词条」，在 `Lookup::Found` 里与真词条并列，会让「查到了」这句话的含义在两种情况下不同：有的能读，有的只是几个数字。术语表里「一无所获」的精确性正建立在这种一致上。

字形是**词条的旁注**，不是词条本身。

## 为什么单独一个库文件

与 `ecdict.db` / `cedict.db` 彼此分开是同一条理由：上游不同、协议不同、升级节奏不同。

Unihan 是 **Unicode License V3**（可用、可改、可再分发、可商用，唯一义务是保留声明），CC-CEDICT 是 **CC BY-SA**（传染性）。两份数据一旦合进同一个文件，署名义务就再也拆不开了。Unicode 每年发一版，届时替换这一个文件即可，碰都不碰另外两个。

## 为什么字形库允许缺席，而两个词库不允许

两个词库缺一不可的理由写在 `OfflineDictionary::open` 上：缺了任一份，对应方向的查询就只能**谎称**「未收录」，而术语表规定那句话的意思是「词典确实没有这个词」。

这条理由**不迁移到字形**。少一份字形，界面只是不显示那一行部首笔画，没有任何一句话变成假的。判据是「缺失会不会让程序说谎」，不是「这份数据重不重要」。故 `unihan: Option<Unihan>`，打不开就当没有——代价若不如此，是所有尚未重建数据的部署直接打不开。

## 数据源的取舍

候选里最热门的两个都不能用，且都不是因为质量：

- **pwxcoo/chinese-xinhua**（16,142 字，star 最多）：仓库挂 MIT，README 却写着「数据都是我从网上收集整理的……本仓库无任何商业目的！如果有侵权行为将及时删除！」。内容抓自《新华字典》，商务印书馆的版权仍在有效期内。仓库作者无权对自己没有的东西授权。
- **g0v/moedict 中華大辭典**：CC BY-**NC-ND**。NC 禁止商用，这一条即已出局。
- **教育部四部國語辭典**：CC BY-ND 3.0 TW，**允许商用**，比上一条宽松得多。卡住它的不是「自建 SQLite」——按 CC 官方说明，单纯的格式转换不构成改编，ND 允许（"in any media or format... even if you have applied a NoDerivatives license"）。卡住它的是**繁简转换**：本项目词头恒为简体（术语表），而繁→简是字词层面的替换，比格式转换离「翻译」近得多，那正是 ND 明确禁止的那一类。判据是「有没有创造性转换」，不是「换没换格式」。
- **mapull/chinese-dictionary**：字段最全（含结构、频率），但 README 自陈「无法确认数据的最初来源，使用它们可能存在风险」。

选 Unihan 的首要理由不是字段多，而是**它是唯一一个来源完全可追溯、且不会哪天被下架的**。

> **后续更正（ADR-0014）**：本节原写「`kMandarin` 每字只给一个音，多音字上明显不如已有的 CC-CEDICT」。那句对 `kMandarin` 成立，但作为对 Unihan 的判断是错的——同一份数据里的 `kXHC1983`／`kTGHZ2013`／`kHanyuPinlu` 是大陆来源的多音字读音，还带频次。用一个字段的性质去判断整个数据集，是那次的错误形状。读音已按 ADR-0014 接入。

这个领域的筛选轴是授权来源的可追溯性，不是数据质量。判据：README 写得出上游、且上游本身自由授权的才算数；写「从网上收集整理」的，那个 LICENSE 文件是装饰。

## 固化的部首表必须被数据反验

`KANGXI_RADICALS` 是 214 个部首的字面量，取自 Unicode 康熙部首区 `U+2F00..=U+2FD5` 的 NFKC 归一。固化是为了不引入一个 Unicode 规范化依赖。

代价是它可能与上游漂移，且漂移**不会有任何东西报错**——产出的每个部首都是错的，程序照常运行。故构建工具在建库前必须调用 `verify_kangxi_table` 拿 Unihan 数据反验：每个部首字自身的 `kRSUnicode` 必须是「该部首号 + 基本形 + 0 笔」。对不上就让建库失败。

不用「部首外笔画为 0 的字即该部首」这条规律直接从数据推全部：它对简化形成立，对基本形会挑中低码位的罕见异体字（部首 102 得到 `曱` 而非 `田`，182 得到 `凬` 而非 `風`）。简化形则只能这么推——Unicode 的「CJK 部首补充区」对它们没有给出 NFKC 归一（实测 113 个字符里仅 1 个有）。

## 后果

- 术语表新增「字形」「部首」「部首外笔画」三个条目，且明确它们是**字**的属性，不是词条的字段。
- `kRSUnicode` 的三个边界情况必须由解析器处理：撇号后缀（3,877 字，忽略会让常用简体字全部显示错误部首）、负的部首外笔画（45 字，故字段是 `i8` 而非 `u8`）、空格分隔的多值（448 字，取第一个）。
- 构建工具扫描 Unihan 目录下**所有** `.txt` 取字段，不按文件名定位：`kRSUnicode` 已经从 `Unihan_RadicalStrokeCounts.txt` 搬到了 `Unihan_IRGSources.txt`，按文件名取在下一次重排时会静默少读。
- 分发物多一个 `unihan.db`（约 3.7MB，102,998 字）。它可缺。
