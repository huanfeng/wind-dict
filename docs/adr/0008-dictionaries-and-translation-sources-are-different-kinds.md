# 词典与译源是两类东西，不统一抽象

查询源分为两类且仅两类：**词典**（查出词条，有出处）与**译源**（产出译文或 AI 生成文本，无出处）。二者不合并为一个统一的「查询源」抽象，且在界面上可区分；AI 译源必须显式标注为生成内容。

## 为什么不统一抽象

统一抽象看起来更优雅，因此这个决定必须记录，否则它一定会被「重构」掉。拒绝的理由有两条：

1. **可信度不同，且用户无从分辨。** 词典的结果有确定出处，查不到就是查不到；AI 译源会流畅地编造不存在的词义。若二者以相同样式并排于两个 tab，用户没有任何线索区分「这是查到的」与「这是编的」。一个词典工具让用户分不清这两者，是失职。这是产品底线，不是洁癖。
2. **数据形状不同，统一必然退化。** 词条有音标、词性、词形变化、收录与否；译文只是一段文本。统一抽象里这些结构字段无处安放，最终只能把词条压扁成纯文本——为了抽象的整齐，牺牲掉离线词典的全部结构优势。

## 触发本决定的事实

调研发现（2026-07）：**有道词典 API 不支持自助开通**，需电话或邮件联系商务。能自助接入的是有道/百度的**翻译** API，而翻译 API 返回的是译文，不是词条。同时唯一免费且无需 key 的 Free Dictionary API 只提供**英英**释义。

也就是说，「在线也做成一个像有道那样的中文词典」这条路对个人开发者是关着的。在线侧能拿到的中文结果，本质上只能来自翻译或 AI——它们**都不是词典**。这个约束不是设计选择，是外部现实；模型必须如实反映它，而不是用命名掩盖。

## 后果

- 「在线 / 离线」降级为查询源的一项**属性**，与「词典 / 译源」的分类正交。`在线词典`、`在线查询` 成为弃用说法——存在在线的词典（Free Dictionary API），也存在必然在线的译源。
- UI 需要**两种结果呈现**：词条式（结构化字段）与文本式（一段话 + 生成标注）。
- 新增 AI 译源时，API key 由用户自备。这也顺带绕开了「分发时共享作者 key」的困境。
- **本项目的分发范围尚未决定**（自用 / 分发给普通用户 / 分发但在线需自填 key）。它影响安装器、key 管理与在线功能的默认可用性，是一个仍然敞开的问题。
