# 英汉词条与汉英词条是两类词条，不合并为一种

词条分为**英汉词条**（源自 ECDICT）与**汉英词条**（源自 CC-CEDICT）两类，用 enum 包住，各自只持有真实存在的字段。不合并成一个「字段并集 + 大量 Option」的统一词条类型。

## 为什么不合并

合并看起来更简单，因此这个决定必须记录，否则它一定会被「简化」掉。两类词条的形状**本就不同**，不存在一个能诚实容纳二者的字段集合：

| | 英汉词条 | 汉英词条 |
|---|---|---|
| 注音 | 音标（IPA） | 拼音（带声调） |
| 释义 | 中文释义 + 英英释义（两个并存字段） | 英文释义（多义项） |
| 词形变化 | 有 | **无——中文不屈折** |
| 繁简对照 | 无此概念 | 有 |
| 量词 | 无此概念 | 有 |

合并的代价不只是「一半字段永远是 None」，而是**类型系统不再阻止无意义的代码**：`苹果` 的「过去式」、`apple` 的「繁体」都会变成可以写出来、可以编译、只在运行时静默返回 `None` 的东西。拆开之后，「给中文词条查词形变化」根本无法通过编译。

这与 ADR-0008 拒绝统一「词典 / 译源」是**同一个论证**：形状不同的东西强行统一，必然退化成最小公分母，牺牲掉各自的结构优势。若那次不统一是对的，这次合并就是错的。

## 触发本决定的事实

实现 CC-CEDICT 接入时发现：`苹果` → `apple` 这个英文解释，既不是「中文释义」也不是「英英释义」——后者按术语表是**英文词头**的英文解释。既有的 `Entry` 类型与术语表都是照 ECDICT 的形状长的，一碰汉英即散架。这不是命名疏漏，是模型确实缺了一层。

## 后果

- 术语表新增「英文释义」「拼音」「繁体」「量词」四个**汉英词条专有**术语，并明确「中文释义 / 英英释义 / 词形变化 / 音标」为**英汉词条专有**。称拼音为「音标」、称汉英的英文解释为「英英释义」，均是本决定被违反的信号。
- UI 层呈现词条时必须 `match` 两个分支。这是接受的代价——它换来的是编译器对「无意义字段访问」的拦截。
- `Lookup::Found` 持有的是包装后的 enum，因此一次查询的结果**同属一类**（方向已由查询词判定，见 ADR-0003），不会混装两类词条。
