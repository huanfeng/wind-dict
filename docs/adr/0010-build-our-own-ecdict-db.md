# 自建英汉词库，不用 ECDICT 官方的 SQLite 发布

ECDICT 官方发布了现成的 SQLite 数据库（`ecdict-sqlite-28.zip`），我们**不用它**，而是从 `ecdict.csv`（76 万词条基础版）自行构建，并在构建期丢弃用不到的列。

## 为什么不用现成的

「上游给了 SQLite，直接用」是显而易见的做法，因此这个偏离必须记录。

实测（GitHub Release API，2026-07）：

| 资产 | 压缩体积 |
|------|---------|
| `ecdict-sqlite-28.zip` | **206.7 MB** |
| `ecdict-stardict-28.zip` | 67.2 MB |
| `ecdict-mdx-28.zip` | 93.2 MB |

官方 SQLite 发布的是 **1.0.28 完整版（约 220 万词条）**，光压缩包就 207 MB，解压后的数据库预计在 600–800 MB 量级。对一个二进制仅约 1 MB 的常驻小工具，这个比例是荒谬的。

而我们并不需要那 220 万词条，也不需要它的全部列：

- **`detail`**（JSON 扩展）与 **`audio`**（官方尚未实现）在本项目中**没有任何用途**，却是体积大头。
- 已决定「中文释义为主、英英释义可展开」，故只需 `word / sw / phonetic / definition / translation / pos / exchange / frq / bnc`。
- 76 万词条的基础版 `ecdict.csv` 已足够——220 万那部分主要是更生僻的长尾。

## 教训：这个决定曾建立在错误的数字上

最初的选择「完整库直接打包进安装器」，是基于一个**估算**：「76 万词条 × 每条约 300 字节 ≈ 200–400 MB」。该估算被明确标注为不可靠，事后证明确实错了——错在算的是 76 万基础版，而官方 SQLite 装的是 220 万完整版，是另一个东西的体积。

本 ADR 不推翻「完整库打包进安装器」这一决定（见 ADR-0006 相关讨论），只修正「完整库」的所指：它指**我们自建的 76 万词条精简库**，而非官方那个 220 万词条的包。

## 后果

- 需要一条**构建期管线**：`ecdict.csv` → 自建 SQLite。这是新增的工程量，且必须与 CC-CEDICT 的解析管线并存（后者上游本就是文本文件）。
- 自建 schema 时**必须保留 `sw` 列与 `(sw, word)` 索引**。ECDICT 原始 schema 中它们专为前缀匹配而设，补全的性能全靠它，见 `store/ecdict.rs` 中的查询计划测试。
- **实测结果（2026-07，`examples/build_ecdict.rs`）**：

  | | 体积 | 词条数 |
  |---|---|---|
  | 官方 `ecdict-sqlite-28.zip` | 207 MB（压缩） | ~220 万 |
  | 自建精简库 | **157.6 MB** | **770,611** |

  自建把 600 MB+ 量级降到 157.6 MB。但**低于本决定预期的「几十 MB」**——预期偏乐观，因为 `ecdict.csv` 本身即 62.9 MB，转入 SQLite 后加索引与页开销近似翻倍。若 157.6 MB 仍不可接受，下一刀是按 `frq` 裁剪词频长尾（当初被否的选项），而非继续丢列。
- 丢弃 `detail` 意味着放弃其中可能有用的扩展数据。这是刻意的：需要时再加回一列，比一开始就背 600 MB 容易得多。

## 修订（2026-08-25）：schema 改为逐列对齐上游，不再裁剪

本 ADR 原先的决定包含两件事：**（一）自建库而不用官方发布**，**（二）建库时丢弃用不到的列**。

第一件维持不变，且理由更硬了——实测官方 `ecdict-sqlite-28.zip` 解压后 **811.9 MB**（原文写的是「预计 600MB+」，估得偏低），而 `ECDICT-ultimate` 的 `ultimate.db` 是 **1162.9 MB**。自建的 157.6 MB 仍是唯一与「常驻小工具」相称的选择。

**第二件推翻**：不再丢列，schema 逐列对齐上游 `stardict.py` 的 `stardict` 表（15 列，含 `id`/`sw`）。

### 为什么推翻

原文的判断是「`collins`/`oxford`/`tag` 当前无功能依赖，`detail`/`audio` 无用途且是体积大头」。实测下来，这个判断的**两个前提都不成立**：

| 列 | 有值条数 / 770,611 | 占比 |
|---|---|---|
| `collins`（柯林斯星级） | 13,633 | 1.8% |
| `oxford`（牛津三千） | 3,461 | 0.4% |
| `tag`（考试大纲） | 14,942 | 1.9% |
| `detail`（JSON 扩展） | **1** | 0.0% |
| `audio`（读音 URL） | **0** | 0.0% |

- **「体积大头」不成立**：`detail` 全库只有 1 条有值，`audio` 一条都没有——官方 README 对二者的标注是「待添加」。它们空着，是功能未实现，不是数据缺失。留着这两列的代价接近于零。
- **「无功能依赖」是自证的**：数据没进库，界面自然无从依赖。而这三列虽然覆盖率只有 1.8% 上下，却**只标常用词**——`support` 一条就带齐了 `collins=5`、`oxford=1`、`tag=gk cet4 cet6 ky ielts`。丢掉它们，丢的恰是用户真正会查的那批词的信息。

一句话：**丢列省下的不是体积，是信息。**

### 对齐格式换来的能力

对齐之后，本项目的词库文件与 ECDICT 生态**双向互换**：官方发布的 `ecdict-sqlite-*.zip`、`ECDICT-ultimate`，以及任何按 `stardict.py` 格式生成的第三方词库，都可以直接替换本库而无需改动一行代码（设置页本就支持指定词库路径，`probe_dict` 负责挡住选错方向的文件）。

这**不与 ADR-0001 冲突**，尽管那份 ADR 写着「用户无法用户词典」。ADR-0001 否决的是 MDX / StarDict 这类**正文为 HTML 的格式**——理由是 windui 没有富文本渲染能力，那个否决至今成立。而这里支持的是**字段化的 SQLite**，每个字段仍是纯文本、仍直接映射到现成控件。两者拒绝与接纳的是不同的东西。

命名上有个坑值得记下：`ecdict-stardict-28.zip` 里的 "stardict" 指**星际译王软件的二进制格式**（.ifo/.idx/.dict），而我们对齐的是 `ecdict-sqlite-28.zip` 内 `stardict.db` 的**表名** `stardict`。同名，两回事——ADR-0001 否决的是前者，本次对齐的是后者。

### 一并厘清的两件事

- **`pos` 列在标准版中 100% 为空**（770,611 条无一有值），故界面上读取该列的分支此前是死代码。它在 `ECDICT-ultimate` 中有 52,527 条有值，因此该列与其渲染分支**予以保留**——它现在的定位是「为外部词库预留」，而非「本库的字段」。界面上真正在用的词性，来自 `domain::parse_glosses` 对 `translation` 文本的解析，与本列无关。
- **`collins`/`oxford` 的空值是 `0` 而非 NULL**（上游声明为 `INTEGER DEFAULT(0)`），与 `bnc`/`frq` 的 `DEFAULT(NULL)` 相反。构建期与读取期都按各自的上游声明处理（`build_ecdict::parse_flag` 对前者、`parse_rank` 对后者；读取侧 `rank_u8`/`rank_u32` 一律把 0 与 NULL 同视为「未知」）。不统一成一种，正是「对齐格式」的含义——读官方库时若把 0 当作有效值，每个词都会被标成牛津核心词。

### 后果

- **旧词库与新代码不兼容**：缺列的库一打开就报「表结构不符」。这符合原文「词库是可整体替换的只读资产，没有迁移这回事」的定位——重建即可，用户数据在另一个库里，不受影响。
- 未采纳 `ECDICT-ultimate`（340 万词条）。实测它多出的 260 万词条**没有带来任何分级信息**——`collins`/`oxford`/`tag` 的有值条数与标准版一模一样（13,633 / 3,461 / 14,942），多出来的全是只有中文翻译的长尾。换它换不来常用词的信息密度，只换来体积。
- 仓库根目录的 `stardict.7z`（49.2 MB，解压为 232.7 MB 的 `stardict.csv`，含完整 340 万词条且随仓库更新）是比 2017 年冻结的 release 更好的完整版来源，若将来需要完整版，应从它构建而非 release。
