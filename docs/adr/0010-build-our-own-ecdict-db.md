# 自建英汉词库，不用 ECDICT 官方的 SQLite 发布

ECDICT 官方发布了现成的 SQLite 数据库（`ecdict-sqlite-28.zip`），我们**不用它**，而是从 `ecdict.csv`（76 万词条基础版）自行构建，并在构建期丢弃用不到的列。

## 为什么不用现成的

「上游给了 SQLite，直接用」是显而易见的做法，因此这个偏离必须记录。

实测（GitHub Release API，2026-07）：

| 资产 | 压缩体积 |
|------|---------|
| `ecdict-sqlite-28.zip` | **206.7 MB** |
| `ecdict-stardict-28.zip` | 67.2 MB |
| `ecdict-mdx-28.zip` | 93.2 MB |

官方 SQLite 发布的是 **1.0.28 完整版（约 220 万词条）**，光压缩包就 207 MB，解压后的数据库预计在 600–800 MB 量级。对一个二进制仅约 1 MB 的常驻小工具，这个比例是荒谬的。

而我们并不需要那 220 万词条，也不需要它的全部列：

- **`detail`**（JSON 扩展）与 **`audio`**（官方尚未实现）在本项目中**没有任何用途**，却是体积大头。
- 已决定「中文释义为主、英英释义可展开」，故只需 `word / sw / phonetic / definition / translation / pos / exchange / frq / bnc`。
- 76 万词条的基础版 `ecdict.csv` 已足够——220 万那部分主要是更生僻的长尾。

## 教训：这个决定曾建立在错误的数字上

最初的选择「完整库直接打包进安装器」，是基于一个**估算**：「76 万词条 × 每条约 300 字节 ≈ 200–400 MB」。该估算被明确标注为不可靠，事后证明确实错了——错在算的是 76 万基础版，而官方 SQLite 装的是 220 万完整版，是另一个东西的体积。

本 ADR 不推翻「完整库打包进安装器」这一决定（见 ADR-0006 相关讨论），只修正「完整库」的所指：它指**我们自建的 76 万词条精简库**，而非官方那个 220 万词条的包。

## 后果

- 需要一条**构建期管线**：`ecdict.csv` → 自建 SQLite。这是新增的工程量，且必须与 CC-CEDICT 的解析管线并存（后者上游本就是文本文件）。
- 自建 schema 时**必须保留 `sw` 列与 `(sw, word)` 索引**。ECDICT 原始 schema 中它们专为前缀匹配而设，补全的性能全靠它，见 `store/ecdict.rs` 中的查询计划测试。
- **实测结果（2026-07，`examples/build_ecdict.rs`）**：

  | | 体积 | 词条数 |
  |---|---|---|
  | 官方 `ecdict-sqlite-28.zip` | 207 MB（压缩） | ~220 万 |
  | 自建精简库 | **157.6 MB** | **770,611** |

  自建把 600 MB+ 量级降到 157.6 MB。但**低于本决定预期的「几十 MB」**——预期偏乐观，因为 `ecdict.csv` 本身即 62.9 MB，转入 SQLite 后加索引与页开销近似翻倍。若 157.6 MB 仍不可接受，下一刀是按 `frq` 裁剪词频长尾（当初被否的选项），而非继续丢列。
- 丢弃 `detail` 意味着放弃其中可能有用的扩展数据。这是刻意的：需要时再加回一列，比一开始就背 600 MB 容易得多。
