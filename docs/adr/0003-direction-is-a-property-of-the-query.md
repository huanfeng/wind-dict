# 查询方向由查询词自动判定，不作为词典维度

英汉与汉英是同一个「离线词典」的两个**方向**，而非两个词典。方向由查询词的文字种类（Unicode 范围）自动判定：输入 `apple` 走英汉，输入 `苹果` 走汉英。tab 只按**词典来源**切分（离线 / 在线），不按方向切分。

## 为什么不做「英汉」「汉英」两个 tab

判断一个字符串是中文还是英文是一次 Unicode 范围检查，成本可忽略。把方向做成 tab，等于要求用户在每次查中文词之前，手动完成一件程序自己就能瞬间判断的事——这是把实现的内部结构泄露给用户。

更关键的是维度爆炸：tab 若同时承载「来源」和「方向」两个维度，tab 数量是两者的**笛卡尔积**。今天是 2×2=4 个，将来加一个日汉词典就是 3×2=6 个。而按来源单一维度切分，新增词典永远只加一个 tab。

## 后果

- **不存在「汉英词典」这个概念**，只存在离线词典的汉英方向。代码与界面中出现 `ChineseEnglishDictionary` 这类命名即是本决定被违反的信号。
- 离线词典内部挂载**两份词库**（英汉、汉英）。「词典」与「词库」由此成为多对多关系，必须严格区分，见 CONTEXT.md。
- 反向查询（如「apple 在汉英词库里被哪些中文词条引用」）在本模型下**无法表达**。这是接受的代价——该需求尚未出现，且真出现时应作为词条页内的关联链接实现，而非一个 tab。
- 查询词若中英混杂或为纯数字/符号，方向判定需要一个明确的默认规则。此规则尚未决定。
