# 发布是一个全量包，且验证发生在压包之前

`scripts/release.ps1` 产出**一个** zip：程序、三份词库、一本示例词典、许可与说明，
按 `Cargo.toml` 的版本命名。压包**之前**先用包里那几份文件真查一次、用包里那个 exe
真起一次。

## 一个包，不是两个

程序约 2.5 MB，词库约 190 MB。分成「程序包 + 词库包」能让补丁版只重下 2.5 MB，
这个好处是真的。仍然合成一个，理由是失败的形状：

分包之后，用户拿到程序仍然**不能用**，还差一步。那一步做错时的表现是——程序打不开，
或者查什么都「未收录」。而这正是 ADR-0016 刚刚花了力气消灭的那一类故障：说不清原因、
且发生在用户没有任何线索的地方。「下载 → 解压 → 双击」必须是一条直线。

代价照实记：**每发一个补丁版，用户与 scoop 都要重下一遍那 190 MB 一字节没变的词库。**
何时该回头改：词库继续变大（比如换一份带例句的英汉库），或发布频率高到用户开始抱怨。
那时切分包只需改动 `release.ps1` 的最后一段——组装（`Copy-Staging`）原样可用，因为
它本来就是按「哪些文件属于哪一类」分组的。

## 验证在压包之前，且验的是暂存目录里的副本

一个发布包真正的失败方式**不是「文件少了」**——那种一眼看得见。是这些：

| 失败 | 用户看到的 |
|---|---|
| 打进去的是 debug 那个 exe | 慢十倍，且它读写的是另一个用户数据目录 |
| 词库是上次 `gen-data` 的半成品 | 装上能启动，查什么都「未收录」 |
| 版本号与 git tag 对不上 | 他报的 bug 指不到任何一个提交 |
| 从有未提交改动的树打的包 | 同上，且根本无法重现 |

四种全都要等用户装上之后才暴露，而那时已经无从查起。所以脚本在压包前做三件事：

1. **版本与 git 状态**。版本号只有一个来源——`Cargo.toml` 的 `[package]` 段；exe 的
   资源版本也从这里来（`CARGO_PKG_VERSION` → `build.rs`），故包名与文件属性天然一致，
   不存在会漂移的第二份。CI 传进来的 tag 只用于**核对**，不作为来源。
   工作树不干净就拒绝打包（`-AllowDirty` 可强行），因为「这个包由哪次提交产生」是
   日后排障唯一的锚点。
2. **拿 `offline_probe` / `mdx_probe` 真查一次**。探的是**暂存目录里的副本**而不是
   `.cache` 里的原件：复制这一步本身就可能漏、可能截断，而「原件是好的」不能证明
   「包里那份是好的」。
3. **用包里那个 exe 跑一次离屏截图**。这是唯一覆盖「exe 与词库放在一起能不能起来」的
   检查——它走完真实的启动路径（`resolve_dict_dir` → `check_dir` → 建窗口 → 渲染），
   而这条路上任何一处失败在 release 下都是**静默**的（`windows_subsystem = "windows"`，
   没有控制台）。

第 3 步有三处不能省的细节，全都是踩过的：**不传词库路径**（默认取 exe 同目录，那正是
用户解压后的样子；传参数反而绕开了要验的那条路）、**沙箱 `LOCALAPPDATA`**（截图模式
会读写设置与历史，打个包顺手清空自己的历史是不能接受的）、**必须有超时**（词库不可用
时 `main` 走 `fatal()` 弹 MessageBox，没人点确定就永远挂着，在 CI 上表现为静默卡死）。

压完还要**回读包内条目与暂存目录逐条比对**：前面所有检查针对的都是磁盘上那堆文件，
而用户拿到的是这个 zip。压缩漏一个文件不会报错。

## 示例词典进包，但装不进去

包里带一本 `dicts-example\ecdict-headless.mdx`，让「用户词典」这条路开箱可试。

但它**不能由安装这一步放到位**：词典目录在 `%LOCALAPPDATA%\wind-dict-data\dicts\`，
在部署目录之外（ADR-0011、ADR-0015），而一个 zip 只能往自己解压的地方写。这个不对称
是设计的直接后果，不是疏忽——把词典目录挪进部署目录就能「自动装好」，代价是卸载时
连用户自己下载的几百 MB 词典一起删掉。那笔交易不划算。

故 `README.txt` 明写这一步，并指向设置页里的「打开」按钮——让用户点一下就能看到那个
目录，而不是让他去理解一条 `%LOCALAPPDATA%` 路径。

## 许可文件必须进包

`THIRD-PARTY.md` 是包内文件，不只是仓库里的一份。`cedict.db` 源自 CC-CEDICT，按
CC BY-SA 4.0 分发，**署名是分发时的义务**；`unihan.db` 的 Unicode License 明写要求
「随数据保留声明」。仓库里放一份不构成履行——拿到 zip 的人没有仓库。

## 包里不套顶层目录，因为 scoop

`New-Zip` 的 `includeBaseDirectory` 是 **`$false`**：解开来就是 `wind-dict.exe` 与那几份
`.db`，外面没有一层 `wind-dict-0.1.0-x64\`。

scoop 是把包**直接解开到应用目录**的。套一层就得靠清单里的 `extract_dir` 顶回来，而那个
字段由 bucket 那边的生成器写不出来——它收到 `repository_dispatch` 后只重写 `version` 与
`architecture.64bit.{url,bin,hash}`。少了 `extract_dir`，装完之后 shim 指向一个不存在的
exe，而那句报错（`Can't shim 'wind-dict.exe': File doesn't exist`）说不清是包错了还是清单
错了。姊妹项目 keyremap 早就是这么定的，两边保持一致。

代价照实记：`Expand-Archive -DestinationPath .` 会把七个文件铺在当前目录。资源管理器与
7-Zip 默认都按包名建一层目录，故这只影响明确指定了目标目录的命令行解压——那时用户本来
就在说「解到这里」。包内 `README.txt` 也改成了「解压到一个**空目录**」。

## scoop 的元数据只有一处来源

`.github/scoop.json` 存名字、`bin`、说明、主页、许可。`release.ps1` 生成清单时读它，
发布工作流通知 bucket 时也读它。抄第二份就等着两边慢慢说出不同的话，而那种不一致的
表现是「`scoop search` 里的说明与 Release 页面上的对不上」——没人会为此报 bug，也就
永远不会被发现。

`release.ps1` 产出的那份 `wind-dict.json` 有两个身份：随 Release 分发的清单，以及**首次
入 bucket 时的种子**。`shortcuts`、`notes`、`persist`、`checkver`、`autoupdate` 这些
自动流程写不出来的字段全靠它带进去；bucket 的生成器保留已有字段，故此后每次发布只覆盖
版本与下载信息。两边形状必须一致，否则第一次自动更新之后会多出或少掉几个字段。

`persist` 是空的，这不是漏写：收藏、历史与设置都在 `%LOCALAPPDATA%\wind-dict-data\`，
本就在 scoop 的 app 目录之外（ADR-0011），`scoop update` / `uninstall` 动不到它们。

`autoupdate.hash` 指向随包发布的 `.sha256`，让 excavator 读那一行而不是把 150MB 拖下来
自己算。那个文件是 `sha256sum` 格式（哈希 + 两个空格 + 文件名），scoop 认得。

## 通知 bucket 时不传哈希

发布工作流只把 `version` / `asset_name` 等发过去，**哈希由对端自己下载资产算**。

传过去反而多一处可能不一致：两边的算法、时序、甚至「算的是不是同一个文件」都得对上，
而那些都是白担的风险——对端本来就要下载那个文件才能确认它存在。

## 后果

- `scripts/common.ps1`：路径与输出辅助从 `dev.ps1` 抽出，两个脚本共用。那些路径是
  同一个事实，抄成两份就等着悄悄漂移。
- `dev.ps1` 补了 UTF-8 BOM。此前它无 BOM，Windows PowerShell 5.1 会按系统 ANSI 代码页
  解释其中的中文注释，失败形式是一个指向随机行号的语法错误——一个极费时的假故障。
- 词库与示例词典由 `dev.ps1` 的 `gd` / `gm` 负责取得，`release.ps1` 只判断在不在、
  缺了就把活交回去。同一件事不写两遍。
- `unihan.db` 在**运行时**可缺（少一行部首笔画不是故障），在**发布时**不可缺：发出去的
  包少了它，每个用户都少这项功能且无从补救。同一份文件，两处判据不同，这是刻意的。
- 脚本是 CI 形状的：全部参数化、无交互、失败即非零退出码，`-NoSmoke` 供无桌面会话的
  runner 使用。`-Repo owner/name` 时顺带生成 scoop manifest——manifest 的核心是下载
  URL 与哈希，而哈希只有这里知道。没给 `-Repo` 就不生成：猜错的 manifest 比没有
  manifest 坏，它会装出一个 404 而不是一句「还没配」。
