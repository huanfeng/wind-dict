# 用户数据独立于部署目录，且不漫游

收藏与历史记录存于 `%LOCALAPPDATA%\wind-dict-data\userdata.db`（debug 构建为
`wind-dict-data-dev`）。这个位置由两条**否定性**约束确定：不在部署目录内，不在
漫游目录内。二者都是为了同一件事——**这份数据必须永不丢失**。

词库反之：它随程序分发、可整体替换升级，与部署目录同生共死。两者的文件边界即是
生命周期边界（见 `src/store/mod.rs`）。

## 为何需要一条 ADR

这条约束**同时约束三处，两种语言**，且没有一处是它的发起方：

| 位置 | 承担的约束 |
|------|-----------|
| `src/main.rs` 的 `userdata_path` | 目录不得与部署目录重合 |
| `scripts/dev.ps1` 的部署目录定义 | 卸载的删除范围不得覆盖用户数据 |
| `src/store/mod.rs` | 不得写 `%APPDATA%`（Roaming） |

`src/store/userdata.rs` 只是**受益方**——它据此选了带回滚日志的 SQLite 持久化，
而非词库那种 `journal_mode = OFF`。

一条被三处遵守、无一处是出处的约束，按定义已是架构决策而非模块实现细节。这不是
形式主义：曾经确实因此出过事——用户数据一度被放在 `%LOCALAPPDATA%\wind-dict\`，
与 `dev.ps1` 的部署目录**逐字相同**，而卸载动作是 `Remove-Item -Recurse -Force`
整个目录。跑一次卸载，收藏与历史一起消失。当时这条约束写在 `userdata.rs` 的模块
文档里，而写路径的人在 `main.rs`、删目录的人在 `dev.ps1`，两边都读不到它。

## 被拒绝的方案

**保留原目录，改小 `dev.ps1` 的删除范围**（改为逐文件删 exe 与两个 .db）。技术上
可行且改动更小。拒绝的理由是：那会让数据的存活依赖**另一个脚本的删除范围写得够
不够小心**。把不变量托付给一个不知道自己在守护它的地方，是这次事故的成因本身，
不该成为它的修复。独立目录则让该不变量不依赖任何人的小心。

**放 `%APPDATA%`（Roaming），让收藏跟着用户换机器走**。拒绝有三条理由，任一独立
成立：

1. 这是个**常驻进程持续打开的 SQLite 文件**。漫游配置在登录/注销时整体同步——
   注销时可能把写到一半的库拷走，两台机器交替登录则是后写者整体覆盖。这与本项目
   特意保留回滚日志换取崩溃安全的用心正好相悖：为「不丢」做的努力，被「漫游」
   一笔勾销。
2. `%APPDATA%` 只在 AD 域漫游配置环境下才真的漫游。消费级 Windows 上「换机器带着
   收藏」多半是想象中的收益。
3. 历史记录一旦漫游，等于把「用户查过哪些词」送出本机、落到域服务器上。对照
   ADR-0002 为隐私拒绝自动兜底的立场，这个默认值过于激进。

**dev 与 release 共用一份用户数据**。拒绝：`dev.ps1` 已刻意把部署目录分成
`wind-dict` 与 `wind-dict-dev`，用户数据层却不隔离是不对称的。跑 dev 构建调试会往
日常使用的历史记录里塞垃圾词；更要紧的是 schema 日后演进（加列、迁移）时，dev
构建会就地改掉 release 正在用的那个库——目前两边 schema 完全相同，
`CREATE TABLE IF NOT EXISTS` 恰好掩盖了这个风险。

## 后果

- **新增任何清理/卸载/重装动作时，必须确认其删除范围不含 `wind-dict-data*`。**
  `dev.ps1` 的部署目录定义处已写有反向锚定注释；若将来引入安装包或清理工具，
  同样的锚定要补上。
- **「可单独备份」由此成立**：用户数据不与 172MB 词库、exe 混在一个目录里，用户
  拷走一个小文件即完成备份。
- `deploy.local.ps1` 可覆盖 `$DeployDirRelease`，理论上能把部署目录指到用户数据
  目录上从而绕开本约束。目前仅靠注释约束；若这条路径日后被实际使用，应在
  `Uninstall` 里加一道断言——用运行时检查兑现「不依赖脚本写得小心」这句话。
- 此前 `src/store/userdata.rs` 曾把这条约束记为 `adr/0006` 的内容，是错的：那份
  ADR 讲的是常驻进程靠 SQLite 按需读页控制内存，全文与用户数据的生命周期无关。
  该错误引用已删除，本文件是这条约束此后的唯一出处。
