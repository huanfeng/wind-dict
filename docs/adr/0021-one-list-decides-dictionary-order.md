# 词典顺序是一份名单，不是三处各排各的

内置词库、自带词典、码表方案，在「先看哪本」这件事上是**同一份名单**
（`Settings::dict_order`，存稳定键）。页签从左到右、同一个词头下的词条从上到下，读的都是它。

## 为什么不分处排

三类来源在实现上确实不同（SQLite / MDX / 拆字表），设置页也分三组列各自的目录与开关。
但「先看哪本」这个问题与它们是什么无关——用户心里只有一份顺序，分三处排等于让他在三个
地方拼出一个结果，还得自己想明白三组之间谁在前。

所以 `TabKey` 也从 `{All, Builtin, User, Code}` 收成了 `{All, Source(键)}`：页签要筛的
只是「这条出自哪一本」，分三个变体的话，每加一类来源就要在筛选、排序、页签三处各补一个
分支，而那三处问的是同一个问题。

## 没排过的排在末尾

`dict_order` 只存用户排过的那些，不在名单里的按 `usize::MAX` 排到末尾，并靠**稳定排序**
保持各自的自然序。

于是新装一本词典时它出现在最后，而不是插进用户精心排好的序列中间某处。反过来——若把全部
来源都写进名单——每次装卸词典都要去维护那份名单，而维护漏了的表现是顺序莫名其妙地变了。

同一来源内部的词条次序**不动**：义项的先后是词典编排的一部分，不是可以随便排的东西。

## 拖完不重建设置页

`reorder_list` 的提交是 `CommitMode::Children`——控件自己已经把行挪到位了。此时再
`bump_settings` 重建整页，会在松手的瞬间把页面换掉，看着像闪了一下，而拖拽的结果本来就
已经在眼前。所以 `move_dict_order` 只落库 + `rebuild_tabs`（页签顺序要跟着变），不重建。

**代价**：这条路径在离屏截图里验不了。`ReorderList` 的提交发生在回落动画结束之后
（见 windui `ui/reorder.rs` 的 `Phase::Settling`：「直接提交会让行瞬移，很跳」），而
`--drag` 在 Up 之后只出一帧。故排序规则由单测钉住（`order_pos` / `sort_entries_by` /
`move_key`），拖拽手感只能人工过一眼。

## 设置页分五类

常规 / 外观 / 词典 / 数据 / 关于。此前十来个组一路平铺，「词典顺序」这种要反复来调的东西
会被埋在第七屏，而它旁边是「快捷键一览」这种读一次就不再看的说明。

左侧那列分类**不跟着正文滚动**（滚动区在右侧内容里面）：跟着滚走的话，翻到长页面的底部
就找不到别的分类了。

## 探测清风输入法时跳过开发版

`source::windinput` 判定安装位置的原则是「那里有没有 `data\schemas`」而不是看名字
（见 ADR-0020），**唯一的例外是开发版**：目录名以 `dev` 结尾的跳过。

开发机上正式版与开发版常常并存，而两者的内置方案是同一套——都列出来的话，设置页会有两行
内容一样的「方案来源」，方案本身还要靠 id 去重才不至于出现两个同名页签。这份重复对用户
没有任何用处。

认名字是这里唯一能认的东西：两者的目录结构与方案数据完全相同，从内容上分辨不出来。这条
约定跟着兄弟项目的安装器走。
